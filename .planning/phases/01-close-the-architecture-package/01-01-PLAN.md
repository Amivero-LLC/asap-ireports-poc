<objective>
Publish the `SpecialistResult` contract (CONT-01) — the typed return value of one specialist
sub-call. The orchestrator says "check this case against 5 CFR 731 financial considerations," the
sub-agent runs its RAG search, and this is what comes back.

Purpose: Phase 2 builds the fan-out against this type. Without it, SPEC-01 has no contract to
return and the deterministic shell has nothing to validate. The block on this contract was lifted
when ADR-012 resolved.

Output: a new domain module, a generated schema file, contract tests, and a corrected
`docs/handoff/contracts.md`.

**The contract is thin, on purpose (D-01).** Three things and nothing else: the criterion analyzed,
the provenance of the run, and the proposed findings with their citations. Every field beyond those
three was considered during `/gsd-discuss-phase` and rejected — a completion-status enum (D-02,
reversed by the user after it was first selected), per-query budget accounting (D-03), a
result-level `information_gaps` list, a tool-allowlist id, and an evidence-considered list. Do not
reintroduce any of them.

**Discretionary decisions made here, so the executor does not have to make them:**
- The criterion-descriptor type is named `SpecialistCriterion`. Nothing turns on the name (D-04
  leaves it to discretion); it is fixed here so the tests and the schema agree.
- `CONTRACT_VERSION` does **not** bump. Adding a root contract changes no existing contract's
  shape, and bumping churns `x-contract-version` in all thirteen existing schema files for no
  consumer. This is recorded as a one-line note in `docs/handoff/contracts.md`, not left implicit.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| specialist sub-agent → orchestrator | Model-generated content is deserialized into `SpecialistResult`. This plan defines the shape that boundary validates against; the boundary itself is enforced in Phase 2. |
| `packages/domain/` → `schemas/` | Generated JSON Schema is published for non-Python consumers. What reaches `schemas/` is a permanent public claim about what this system will emit. |
| contract set → human reviewer | Any field published here can eventually surface to an adjudication officer. |

No network surface, no user input, no authentication, no data store is introduced by this plan.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Elevation of Privilege | `SpecialistResult` published to `schemas/` | mitigate | An aggregate score, risk level, or recommendation field would let the system emit a determination, breaching the decision-support boundary (ADR-014). Mitigation is the existing `test_no_contract_carries_an_aggregate_score`, which walks every schema in `ROOT_CONTRACTS` through `$defs` — Task 1's `ROOT_CONTRACTS` registration is what puts the new contract under that test. Not duplicated in Task 2 by design; the acceptance criterion instead requires the existing parametrized test to pass with the new stem present. |
| T-01-02 | Information Disclosure | `tests/contract/test_specialist_result.py` fixtures | mitigate | Test fixtures are the classic place real case text leaks into a repo. Synthetic data only, always (`CLAUDE.md`). Task 2's acceptance criteria require no real names, no real case numbers, and no concrete model id in the file. |
| T-01-03 | Tampering | `packages/domain/` contract instances | mitigate | A machine proposal edited in place would defeat ADR-011's "both versions retained." Mitigated structurally by `ContractModel`'s `frozen=True`, asserted directly in Task 2 test 5. |
| T-01-04 | Tampering | `schemas/` drift from the models | mitigate | A schema file that no longer matches its model is a silently wrong public contract. Mitigated by `scripts/generate_schemas.py --check`, run as an acceptance criterion in Task 1 and Task 3 rather than left to a final sweep. |
| T-01-05 | Repudiation | run/finding provenance | accept | `GeneratedBy` (`node`, `model_alias`, `prompt_version`) plus `run_id`/`case_id` is the provenance this contract carries. Per-call cryptographic attestation is out of scope for the spine and is not claimed anywhere. |
| T-01-06 | Spoofing | — | n/a | No authentication or identity assertion exists in this plan; nothing authenticates to anything. |
| T-01-07 | Denial of Service | — | n/a | No runtime service, no request path, no resource allocation under attacker control. Pydantic validation runs in-process on orchestrator-supplied data only. |
| T-01-SC | Tampering | package installs | n/a | This plan installs no packages. `specialist.py` imports only from `pydantic` and sibling modules already in the pinned dependency set; no `uv add`, `pip install`, or lockfile change occurs. If an executor finds itself needing a new dependency, stop — that is out of scope for CONT-01. |

**ASVS L2 scoring:** V5 (validation) is the only chapter with live surface here and is addressed by
`extra="forbid"`, the typed identifier patterns, and the criterion-consistency validator. V2 (auth),
V3 (session), V4 (access control), V7 (crypto), V12 (files), V13 (API) have no surface in this plan.
No `high`-severity finding is expected; `bandit` and `pip-audit` must stay clean.
</threat_model>
